## Compute and layout

- **Budget:** 3 boxes × 6 days = **432 billed box-hours** (`05` §2.2). That's 1 learner + 2 actor
  boxes, counted by `fleet.py` over every box the run rents, failed attempts and replacements
  included.
- **Launch** (from a clean commit):

  ```bash
  F="python3 tools/fleet/fleet.py"
  $F up --run p0-a --config experiments/configs/p0.toml --init workdir/pilot/qs-a/pilot-qs-a-final.pth \
      --actors 2 --procs 2 --set dataset.num_workers=4 --hard-hours 156 --verify --yes
  setsid -f $F watch --run p0-a --replace --budget-box-hours 432 --snapshot-at 0.25,0.5 \
      --max-dollars 450 > workdir/fleet/runs/p0-a/watch.out 2>&1 < /dev/null
  ```

  `watch` freezes `p25` and `p50` at 108 and 216 box-hours, then `full` at 432, and tears the
  fleet down. The watchdog (156 h ≈ 6.5 days) is the backstop if `watch` dies. `--max-dollars
  450` is a safety stop well below the $500 line. Both the watchdog and `watch` run on the
  workstation, so it must stay on and awake for the whole run.
- **Tuning allowance** (decided 2026-10-09, ≤ 1 box-day, `05` §2.2). Only throughput and staleness
  are tuned, never learning hyperparameters: P0 is the released recipe plus fixes.
  - **Actor batch: 800 games** (p0.toml as is). 2,000-game batches give +28% actor rate but a
    policy lag of mean ~2 and max 4 (`experiments/fleet-host-benchmarks.md`), against the soak's
    p95 ≤ 2. The learner is the bottleneck anyway, so the extra games would wait in the queue.
  - **2 client processes per actor box.** Two actor boxes then produce ≈ 132K hanchan/h, more than
    the learner's ≈ 85K/h, so a third process would only add queueing.
  - **Learner loader workers: chosen by a short check before the run,** on its own rented box
    (fleet run `p0-tune`), outside P0's 432 box-hours.
    - Command: `tools/fleet/bench_learner.py --versions 4 --workers 2 4 8 --games 1600`.
    - Rule: pick the fastest `full` samples/s; a count within 5% of the fastest loses to fewer
      workers.
    - Applied with `--set dataset.num_workers=N`. Data loading only, so what P0 learns is
      unchanged.
    - *Amendment, 2026-10-09, before any timing:* on the first check box (EPYC 7C13), the
      benchmark hung in `torch.compile`'s first compilation for 45 min. The `full` passes
      therefore run eager (`--no-compile`). The learner is bound by data preparation (~3.7K
      samples/s against a ≥ 10K GPU ceiling), so compilation doesn't change which worker count
      is fastest. The rule is otherwise unchanged.
    - **Result (2026-10-09; Vast EPYC 7C13, 30.7-CPU quota, RTX 4090; 1,600-game drain,
      254K samples, eager; `workdir/fleet/runs/p0-tune/learner-workers.json`; $0.49):**

      | Loader workers | Full, samples/s | Data only, samples/s |
      |---|---|---|
      | 2 (p0.toml) | 3,601 | 3,486 |
      | **4** | **4,841** | 5,333 |
      | 8 | 4,726 | 5,676 |

      GPU only (eager): 24,766 samples/s. **Choice: 4 workers.** It is the fastest; 8 is within 5%
      and has more workers. Learner capacity rises ≈ 34%, to ≈ 4.8K samples/s ≈ 110K hanchan/h,
      about what two actor boxes produce.

## Incidents during run p0-a

- **2026-10-09 23:50 UTC, learner box lost** (Vast `instance exited`). `watch` replaced it in
  1,175 s, inside the soak's 30 min, and pushed the last pulled checkpoint (step ≈ 188K, from the
  23:24 pull).
- **2026-10-10 02:03, trainer wedged.** A DataLoader worker died with `Too many open files`: Vast's
  soft limit is 1,024, and 4 workers on a 3,200-log drain share tensors by file descriptor. The
  trainer stayed alive with the GPU at 0%, and health only warned (queue full).
  - **Fixed** (`05cca12`): `box_supervise.sh` raises the soft limit to the hard limit; health
    reports `trainer stalled` (no parameters for 15 min with the queue full) as a fail, and
    `watch` restarts the unit.
- **2026-10-10, both learner starts discarded the training.**
  - `fleet.py start` created the checkpoint with `[ -f state ] || [ -f init ] && cp init state`,
    which bash parses as `([ -f state ] || [ -f init ]) && cp …`. Every learner start therefore
    replaced the checkpoint with pilot A: the 00:14 replacement (discarding ≈ 32K steps) and the
    02:14 restart after the stall fix (discarding ≈ 41K steps, at 197,200).
  - **Fixed** (`d06a10d`), with a test that the old line fails.
  - **Accounting:** training effectively restarted from pilot A at **02:14:11 UTC**.
    `fleet.py rebase` excludes the 12.6 box-hours before that from P0's 432, so p25/p50/full
    count from 02:14 and the snapshots are a clean run from the init. The ≈ $6 discarded counts
    in spend, not compute.
  - **Consequence:** the run ends ≈ 2026-10-16 02:15 UTC, still inside the 156 h watchdog
    (10:01 UTC).

## Policy lag during run p0-a (finding, 2026-10-10)

- **Measured** from the learner's tensorboard (`workdir/fleet/runs/p0-a/learner-run/tb/`):
  2026-10-10 02:14–18:40 UTC, steps 156,400 → 705,200, the first hour left out as ramp-up, one
  value per 400-step interval.

  | Per interval | Median | p95 | Max |
  |---|---|---|---|
  | Policy lag, mean (versions) | 7.1 | 8.8 | 24 |
  | Policy lag, max (versions) | 8 | 11 | 44 |
  | Ratio p99 | 1.34 | 1.41 | 1.52 |
  | Clip fraction | 5.6% | 7.4% | 9.4% |

  - Excluded fraction 0; first-minibatch ratio means 0.976–1.064.
  - In learner steps, a lag of 7 versions is ≈ 2,800 steps, ≈ 5 min.
  - The maxima come from two short episodes, 12:43–12:53 UTC (lag max 44) and 14:48–14:51
    (max 19). Neither matches a fleet event. Not investigated.
- **Against the plan:**
  - The fleet soak (`03` §3, item 7, a gate for T1) requires lag p95 ≤ 2 parameter versions. This
    fleet runs at ≈ 9–11, 4–5× over.
  - The tuning allowance above expected 800-game batches to keep lag under 2. That figure came
    from a single actor process (`fleet-host-benchmarks.md`: mean 0.4, max 1), with the learner
    busy for only 54 s of each 131 s cycle.
- **Why** (inferred from the rates, not traced):
  - A version is 400 learner steps. At the measured 33.5K steps/h, that's one version every
    ≈ 43 s.
  - An 800-game batch plays on one parameter version. It takes ≈ 90 s per process on the 9684X
    (≈ 32K games/h) and ≈ 125 s on the 7C13 (≈ 23K/h).
  - Its games reach the learner only when the batch ends, so they are already 2–3 versions old
    before any queueing. Waiting for the next drain and the drain's own training add the rest.
  - In the benchmark, the learner sat idle for most of each cycle, so few versions passed during a
    batch. Lag in versions grows with learner utilization: a fleet balanced to keep the learner
    busy also has the most lag.
- **Effect on P0: none the plan acts on.**
  - The PPO ratio uses stored behaviour probabilities, so it corrects for the lag.
  - The plan's trigger for off-policy correction (V-trace, `05`: lag pushing the ratio p99 above
    2) is far off.
  - P0 continues unchanged.
- **B0 had the same lag:**
  - lag-mean median 6.5 (`p1a-b0`) and 6.3 (`p1b-b0`), p95 7.7 in both; lag-max p95 9;
  - P1 runs on the same fleet shape, so expect the same there.
- **Open, for the user, before the T1 soak:**
  - **Shorter actor batches** (e.g., 200–400 games) would cut the 2–3 versions each batch
    carries, at some cost in actor rate: going from 800 to 2,000 games gave +28%. Changing this
    for P1 alone would make P1's staleness differ from P0's.
  - **Lag in versions depends on `submit_every`.** Publishing less often lowers the version
    count but makes the data staler in learner steps. A criterion in learner steps or minutes, or
    on the ratio itself, would measure staleness directly. Changing the soak criterion is a gate
    change, so it needs an `08` entry first.

## Caveats, stated before the result

- **One run.** The ½ → full gain is this run's. Training luck (~±0.003 u per network in the SP
  ablation, `sp-ablation.md` §6) partly cancels within a run, since both checkpoints share the
  first half of it, but the gain itself still varies between runs.
- **Quick model.** It starts from a b8c192 BC student. Gains per doubling from a stronger start
  may be smaller.
- **Engine, not mahjong.** If P0 doesn't learn (Equim's early PPO didn't, `01` §2), the estimate
  is ≈ 0 for this engine. That says nothing about RL in general, and P1/V/H supply their own
  checkpoints (`05` §2.2).
